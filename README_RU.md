# whitehttpd

Два независимых HTTP-сервера в одном дереве. Оба написаны с нуля под ABI ядра
Linux, не используют libc, не выделяют память в куче и отвечают на запросы
только из статических буферов. Архитектура Си-сервера построена на прямых
системных вызовах без libc (`nolibc`), что делает код переносимым на любые
встраиваемые архитектуры Linux (включая x86-64, MIPS BE/LE, ARM/AArch64 и RISC-V).

## 1. `final-4092/` - whitehttpd (final-4092 as MIPS BE), 4 092 байта

Исходник под GNU as для MIPS32r2 big-endian, заморожен. Один файл
`whitehttpd.s`, 1347 строк. Весь бинарник занимает одну страницу памяти
4096 байт и одну запись в TLB.

**Что умеет**

- `GET` и `HEAD`, HTTP/1.0 и HTTP/1.1
- Keep-Alive и pipelining
- поиск `index.html`
- редирект 301 на каталог без завершающего слеша
- `Range: bytes=N-M` с ответом `206 Partial Content` и `Content-Range`
- 14 MIME-типов, `charset=utf-8` для `text/*`
- защита от симлинков и обхода пути: `O_NOFOLLOW` на каждом компоненте
- IPv6 dual-stack: один сокет `AF_INET6` с `IPV6_V6ONLY=0` принимает оба семейства
- событийный цикл `epoll`, таймаут запроса 3 с
- коды 200, 206, 301, 400, 403, 404, 501

**Чего нет по контракту**

- TLS
- листинга каталогов (403)
- `--addr`
- аутентификации
- `ETag`, `Last-Modified`, `Date`
- `OPTIONS` (отвечает 501)
- CGI, сжатия, HTTP/2, конфиг-файла

Целевое железо: ASUS RT-AC57U V3, QCA5502, Linux 3.3.8, прошивки класса
OpenWrt и Padavan. Проверен на реальном устройстве, не только в эмуляторе.

## 2. `whitehttpd_c/` - полный сервер, три цели

Freestanding C на nolibc, одно дерево исходников: `src/httpd.c` и `src/wsock.h`.

| Цель | Размер |
| --- | ---: |
| `whitehttpd-nolibc-x86_64` | 17 008 |
| `whitehttpd-nolibc-mips32be` | 20 892 |
| `whitehttpd-nolibc-mips32el` | 20 908 |

**Всё, что умеет ассемблерный эталон** - `epoll`, IPv6 dual-stack на одном сокете
`AF_INET6` с `IPV6_V6ONLY=0`, `Range` с `206`, коды 200/301/403/404 -
**и сверх этого**

- листинг каталогов с экранированием HTML, ограничение 64 КиБ
- `--addr` для привязки к конкретному адресу, IPv4 или IPv6
- `ETag` и `If-None-Match` с ответом `304 Not Modified`
- заголовки `Last-Modified` и `Date`
- `OPTIONS` с ответом `200` и `Allow: GET, HEAD, OPTIONS`
- `405 Method Not Allowed` на остальные методы
- рабочие процессы, `MAX_WORKERS 16`; по умолчанию работает 4 процесса,
  замерено на x86-64, на ASUS RT-AC57U V3 (MIPS BE) и на MediaTek MT7628 (MIPS LE)
- `X-Content-Type-Options: nosniff`

**Архитектура**

Ядерный мультиплексор `sys_epoll`, префорк рабочих процессов, статические
буферы в `.bss`, прямые системные вызовы без libc, собственные неблокирующие
конечные автоматы. Ни `malloc`, ни `snprintf`.

**Чего нет**

TLS, CGI, сжатия, HTTP/2, конфиг-файла, аутентификации.

Из коробки настроены и верифицированы цели x86-64 и MIPS32 O32 (BE и LE).
Перенос на другие архитектуры Linux (ARM, RISC-V) выполняется простым подключением
соответствующего заголовочного файла `arch-*.h` из апстрима nolibc ядра.

### 5.4 Декларация Clean-Room реализации (Независимость от darkhttpd)
Сервер `whitehttpd` (как ассемблерный профиль MIPS32 `whitehttpd.s` / `whitehttpd.s`, так и freestanding Си-реализация `httpd.c` + `wsock.h`) является полностью независимой чистой реализацией (Clean-Room Implementation). Он **не** является форком, производной работой или адаптацией `darkhttpd` (Emil Mikulic, лицензия ISC) и не несёт перед ним лицензионных обязательств по следующим причинам:
- **0% общего кода**: ни единой строки исходного кода, структур данных, алгоритмов или функций не скопировано и не заимствовано из `darkhttpd.c`. Вся кодовая база спроектирована и написана с нуля.
- **Принципиальные архитектурные различия**:
  - `darkhttpd` опирается на стандартную libc, однопоточный мультиплексор `poll()`, динамическое выделение памяти в куче (`malloc`, `realloc`, `free`) и форматирование строк через `snprintf`.
  - `whitehttpd` полностью исключает кучу (zero malloc), не использует libc, работает на прямых системных вызовах ядра Linux (`syscall`), мультиплексоре `epoll`, многопроцессном префорке (prefork) и статических кольцевых буферах состояний в секции `.bss`.
- Сторонние компоненты и их лицензии перечислены в [NOTICE](NOTICE) и [LICENSES/](LICENSES/).
- Политика безопасности: [SECURITY.md](SECURITY.md).

## 6. Область применения

Это не замена nginx или Apache. Оба сервера закрывают намеренно узкий контракт:
отдача статики из одного каталога, безопасно и с минимальным потреблением
памяти. Годится для публичной статики на современном ядре Linux из отдельного
каталога без секретов, под непривилегированным пользователем.
